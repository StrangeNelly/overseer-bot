# Critic pass: gaps and contradictions

## Gaps flagged (each got a follow-up agent)

- Groupie is a read-only dashboard tracking memecoin 'calls' in a Telegram group, v1 on Robinhood Chain (Arbitrum Orbit L2, chain ID 4663, mainnet live since 1 July 2026), planning to use the free DexScreener API (chainId 'robinhood', endpoint api.dexscreener.com/tokens/v1/robinhood/{addresses}) and free GeckoTerminal API (network 'robinhood') as its only market-data sources. Most group calls happen at or seconds-to-minutes after token launch on pump.fun-style launchpads on that chain (hood.fun, Noxa at fun.noxa.fi/robinhood, PONS), i.e. often BEFORE the token graduates from its bonding curve into a Uniswap pool. Research question: do the DexScreener and GeckoTerminal APIs index Robinhood Chain launchpad tokens during the pre-graduation bonding-curve phase, and what is the typical indexing latency for a brand-new token/pair after creation? If bonding-curve tokens are NOT covered (or latency is minutes+), what concrete free-or-cheap alternative supplies price and market cap for pre-graduation tokens — e.g. GeckoTerminal's launchpad_details field, Codex.io's launchpad lifecycle queries, the launchpads' own public APIs, or another aggregator? This determines whether Groupie can capture 'market cap at call time' for launch-time calls at all, which is the app's core number.

- For Groupie's 'died after call' section (a headline v1 feature) on Robinhood Chain: when a memecoin dies — liquidity pulled/rugged, or trading simply stops — what do the free DexScreener API (api.dexscreener.com/tokens/v1/robinhood/{address} and /latest/dex/tokens/{address}) and the free GeckoTerminal API (api.geckoterminal.com/api/v2/networks/robinhood/...) actually return for that token afterwards? Specifically: does the pair remain queryable indefinitely with near-zero liquidity/price, does the response become an empty array/404, and do these aggregators ever delist or hide scam-flagged pairs so that a dashboard polling them would silently lose the token? Which response fields (liquidity.usd, volume.h24, txns counts, priceUsd) reliably distinguish a dead/rugged token from a merely quiet one? Answer empirically by finding 2-3 known rugged/dead Robinhood Chain token addresses (e.g. via dexscreener.com/robinhood sorted by age with drained liquidity) and probing the live API responses for them. Without this, the death-detection logic and the retention/polling-decay policy for dead tokens cannot be specified.

- Groupie may need direct on-chain access to Robinhood Chain (chain ID 4663) as a fallback for launchpad-phase token data and for detecting new launches the instant a monitored project goes live. Two facts are unverified: (1) What are the current (September 2026) free-tier limits of Alchemy for the robinhood-mainnet network (https://robinhood-mainnet.g.alchemy.com), and does the free tier include WebSocket eth_subscribe log subscriptions and eth_getLogs at rates workable for a chain with 100 ms blocks? Also check free tiers of the other officially listed RPC providers (QuickNode, dRPC, Validation Cloud) and of managed indexers with claimed Robinhood support (Envio HyperIndex/HyperSync, Goldsky, The Graph). (2) What are the actual deployed contract addresses and event signatures on chain 4663 for the major launchpads — hood.fun token-creation and its Migrator 'graduation to Uniswap v3' event, Noxa, and PONS — and for the Uniswap v4 PoolManager (the v2/v3 factory addresses are known: v3 factory 0x1f7d7550b1b028f7571e69a784071f0205fd2efa)? These come from each launchpad's docs or the Blockscout explorer at robinhoodchain.blockscout.com (note: that explorer's API returned a Cloudflare challenge from a datacenter IP — also verify whether its REST API is usable from a hosted server). Without these, the plan cannot commit to an aggregator-only vs aggregator-plus-chain-events ingestion architecture.

## Contradictions (with resolutions)

- CRITICAL — Can Groupie's Bot API bot read Rick/Phanes messages? auth-architecture claims that disabling privacy mode or making the bot an admin lets it read 'all messages (Rick/Phanes posts, raw CA pastes)' and its recommendation depends on this ('Detect calls primarily from ... Rick/Phanes reply text and buttons (harvest at-call mcap from Rick)'). telegram-ingestion says the opposite: even as admin, a Bot API bot never receives other bots' messages. RESOLVED by live fetch of https://core.telegram.org/bots/faq (1 Sep 2026): 'bots will not be able to see messages from other bots regardless of mode' and 'Bot admins and bots with privacy mode disabled will receive all messages except messages sent by other bots.' telegram-ingestion is correct; auth-architecture is wrong. Implementation consequence: Groupie cannot parse Rick/Phanes call cards or harvest Rick's at-call market cap via the Bot API — it must extract contract addresses from human members' messages and compute call-time market cap from its own market-data feed (which raises the stakes on the launchpad-phase data gap above).

- Banana Gun on Robinhood Chain: robinhood-chain says YES, day-one support; trading-links-competitors says 'No Robinhood Chain support found -> skip for v1' and lists Banana Gun as ETH/Sol/Base/Blast only. RESOLVED: Banana Gun's official blog (https://blog.bananagun.io/blog/banana-gun-robinhood-chain) confirms Robinhood Chain trading (market buys, limit orders, copy trading) in the same Telegram bot from the moment the chain opened to bots. robinhood-chain is correct; Banana Gun is a legitimate v1 link-out candidate (its documented deep-link format t.me/BananaGunSniper_bot?start=snp_{refID}_{tokenCA} from trading-links remains useful).

- Bloom on Robinhood Chain: robinhood-chain says YES (chains: Solana, Ethereum, BSC, Base, Robinhood, Arc, HyperEVM); trading-links-competitors says Bloom is Sol/BSC/ETH/Base only, 'No Robinhood support -> skip for v1'. RESOLVED: Bloom's own site and docs (https://www.bloombot.app/, https://docs.bloombot.app/) list Robinhood Chain as supported. robinhood-chain is correct; Bloom is also a viable v1 link-out (token-embedded deep-link format still unverified per trading-links).

- Minor — latest grammY version: telegram-ingestion says v1.46.0 (implements Bot API 10.3); auth-architecture says v1.45.1 on npm. Not independently re-verified; likely just a release landing between the two agents' checks. No design impact — both agree grammY is current and healthy and Telegraf is stagnant.

## Notes

Spot-checks performed live on 1 Sep 2026: core.telegram.org/bots/faq (bot-to-bot message visibility), blog.bananagun.io/blog/banana-gun-robinhood-chain (Banana Gun Robinhood support), bloombot.app + docs.bloombot.app (Bloom Robinhood support). Net effect of the resolutions: (a) the ingestion design must follow telegram-ingestion's model — the Bot API bot sees only human messages, so mcap-at-call comes from Groupie's own market-data lookup at ingest time, making gap 1 (launchpad/bonding-curve coverage and indexing latency) the single most important unanswered question; (b) trading-links-competitors' 'confirmed Robinhood venues' list is too conservative — Banana Gun and Bloom should be restored as link-out candidates alongside Axiom, GMGN, Maestro, DexScreener, OKX. Everything else across the six summaries is mutually consistent, including the two independent confirmations of the surprising 2026 Telegram OIDC login change, DexScreener/GeckoTerminal Robinhood support (both verified via live API calls by two different agents), Robinhood Chain facts (1 Jul 2026 mainnet, chain ID 4663, ETH gas), BullX's June 2026 shutdown, and the X API's 2026 pay-per-use pricing. Items deliberately NOT listed as gaps because they are product/user decisions, not web-researchable facts: whether human messages always contain the raw CA, group owner consent to add the bot as admin, backfill appetite, TypeScript vs Python, budget ceilings, referral-code ownership, and the exact 'died' threshold definition (though gap 2 supplies the API facts that definition must be built on).
